# v6 与 v11：系统设计负优化审计

日期：2026-10-03。这里比较通用 RSI 实现、固定 prompt 和实际发送的上下文，
不把某次 LLM 生成了更好的算法直接当成系统设计的因果证据。

Spooky 的历史 v6 最佳 log loss 为 **0.31482771348040794**，
v9 为 **0.37690144272122**，v11 为 **0.3542728330169538**。
v11 的保存预测已独立复评，确实落后于 v6 和 MLEvolve 的 0.345936。
本次修复后的 v12 独立复测最佳为 **0.32986289055145557**，20 个已测轮次，
于 2026-10-04 完成；改善了 v11，但仍未恢复 v6。
完整结果与新发现的实现缺口见 [v12 复测报告](SPOOKY_V12_EVALUATION_20261003.md)。

## 比较依据与边界

- v6：`no-use/benchmarks/mle_bench_lite_spooky/runs/graph_evolve_5h_20260930_v6`。
- v9：`benchmarks/mle_bench_lite_spooky/runs/graph_evolve_5h_20261002_v9`。
- v11：`benchmarks/mle_bench_lite_spooky/runs/graph_evolve_5h_20261003_v11`；
  运行源代码修订为 `5a446c8`，20 个已测研究轮次。
- 每次运行的 `.methodtrail/llm_calls.jsonl` 保存了实际发送的固定指令和上下文。
  `.methodtrail/artifacts.sqlite` 保存压缩前的 `research_state`，因此可以确定
  信息是没有产生，还是产生后被 prompt 打包器丢弃。
- v6 在当时尚未提交的工作区运行，不能把后续汇总提交 `32da37f` 当成
  精确锁定的 v6 源代码。v6 的实际指令和上下文以保存的请求为准；
  `32da37f` 用于重建当时的代码机制，明确区别于完整运行源码快照。

## 1. 压缩上下文错误地删除了经验的结构信息

**因为新版用不匹配实际数据结构的字段白名单压缩上下文，导致 v6 能读到的
经验类别与组件，在 v9/v11 进入 Agent 前被删除。**

`1a2e8ed` 引入的 `_compact_state` 只保留经验图摘要的
`nodes/edges/families/summary/recent`，而 `MemoryGraph.profile()` 实际返回
`card_count/decisions/method_families/linked_card_count`。结果是摘要变成 `{}`。
同一压缩流程复用 `_compact_node` 处理经验卡片，又遗漏 `card_id`、
`method_family`、`method_components`、`changed_factors`、检索来源和相关性。

实际保存的上下文统计如下。卡片行数含同一卡片在不同调用中重复出现，
不是独立卡片总数。

| 实际发送的信息 | v6 | v9 | v11 |
| --- | ---: | ---: | ---: |
| 含 state 的调用 | 98 | 31 | 130 |
| 含非空经验图摘要 | 98 | 0 | 0 |
| 经验卡片行数 | 475 | 80 | 643 |
| 保留卡片 ID / 方法族 / 组件的行数 | 475 / 475 / 475 | 0 / 0 / 0 | 0 / 0 / 0 |

直接影响：Agent 仍读得到一些指标和结论，但无法从这些卡片的结构字段
可靠区分“什么方法、改了什么因素、证据从哪里检索来”。方法图中另有
部分方法信息，不能据此说 Agent 完全不知道方法，也不能说两张图消失了。

本次修复保留真实摘要字段及卡片元数据，也保留调用者提供的有向检索路径。
需要特别区分：v6 和 v11 保存的卡片均没有 `memory_graph_trace`；
因此不能把“v11 丢了有向溯源路径”当成已观察到的版本差异。
方法图的 `edge_trace` 本来就有保留。

## 2. 按时间截取候选池，弱化了未探索分支的可见性

**因为新版把方法池简单截成最后 36 个节点，导致早期未运行的分支
在后续提出候选时被较新的记录挤出上下文。**

v11 最后一个保存的研究 state 有 50 个方法节点。旧打包器只发送最后
36 个，遗漏 6 个仍为 `proposed/ranked` 的候选节点。这 6 个也没有出现在
该阶段的相关方法上下文中。其中包括带校准的线性 SVM 组合特征方向。
另有 1 个 `selected` 节点也被截掉。

这里说的是 6 个未执行状态的**图节点**，不是 6 种从未试过的独立算法；
其中一些有后来运行的相近方案。磁盘候选池没有被删除，选择 Agent
还会单独收到当轮可行候选。因此问题是生成阶段容易忘记未探索分支，
不是所有被截掉的候选从此不可选择。

本次改为先保留当前最好版本及相关已测节点、待执行分支，再补近期历史。
较小预算的二次截取保留优先排序的头部，而不是再次取尾部。
回放同一个 v11 state，以上遗漏节点全部恢复，发送节点数仍为 36。

## 3. 跨方法经验迁移把“同字段名”误当成“同组件”

**因为后续新增的相似度规则把组件字段名相同视为方法相近，导致新方向
会受无关方法的坏结果和耗时影响；v6 时期的保守校准没有这一条规则。**

`7fd8712` 新增的 `_method_similarity` 对组件键或值有交集的方案给
0.65 相似度。两个方案都使用 `features`、`classifier` 这样的字段名，
即使方法族、组件值、改动因素完全不同，也会触发经验迁移。
这是 v10/v11 所含的新机制，不能倒推为 v9 落败的原因。

确定性反例：A 方法四次比父版本差，B 方法与 A 完全无关，但用了同样
的组件字段名。将同一候选与同一历史交给三个实现，得到：

| 校准结果 | v6 时期代码机制 | 修复前 v11 机制 | 本次修复后 |
| --- | ---: | ---: | ---: |
| 预计增益 | 0.100 | 0.035 | 0.100 |
| 预计执行时间（秒） | 50 | 212 | 50 |

这会直接改变候选的程序评分与可行性估计，因果链可复现。
它不证明 Spooky 的整个分数差距由此产生。
修复后要求同一组件键对应的实际组件值一致，或存在原有的同方法族、
共享改动因素证据；保留真实跨方法证据迁移。

另一个上下文缺陷也已修复：候选评分摘要原先遗漏程序实际计算的
方法族实验数、未提升次数、新因素、因素停滞及评分倍率等字段。
现在选择 Agent 能读到这些判断依据，而不仅是笼统的类别标签。

## 4. 选择 prompt 给重复验证过于宽泛的理由

**因为新版把“有提升、验证与独立评测不一致、曾被采纳”写成足以重复
验证的理由，同时弱化了保留探索替代分支的要求，导致选择规则更容易
继续验证当前路线。**

这项差异来自保存的固定 prompt，不是从候选标题推断。
v6 的选择 prompt 没有上述充分理由；后续版本明确加入了它。
不同数据划分的得分天然可能不同，“曾被采纳”也不会自动失效，
所以该条件不能有效判断什么时候验证已经足够。

与此同时，v6 后续候选 prompt 要求在存在未测互补因素时保留替代
挑战者；修复前新版改成了较弱的“考虑”替代挑战者。

本次将重复验证改为必须说明具体未解决的测量疑问、比较协议和结束条件；
要求未探索因素有可执行的替代分支，可以复用已有候选。
仍由 Agent 决定具体方法和候选数量，没有加入任务专属算法或强制组合。
这确认了指令倾向的变化；它对最终分数的影响还需对照运行验证。

## 共有缺陷，不能冒充新版负优化

v11 第 15–20 轮没有带来新的分数提升，研究持续围绕归一化、验证及
输出诊断。最终预测的最大概率行和误差为 `1.2014e-7`，在评测器容差内；
显式归一化后复评仅改变约 `7e-9`。

这里暴露的旧缺陷是：成功运行的 stderr 警告也进入评估上下文，
评估选择 `evidence` 后会再次生成验证问题，控制器没有结构化记录
“疑问已关闭、证据已经重复”。v6 和 v11 的 Assessment/Evidence 指令
及这一控制分支一致，不能说新版新加了这个坏循环。
本次收紧选择指令，但尚未实现疑问关闭的结构化控制状态，不能称已根治。

以下差异也不能直接认定为负优化：

- v6 已有实现审查，不是新版才加入一个审查 Agent。
- v6 的 OOF stacking、ComplementNB 替换、BM25 来自那次模型生成，
  不在保存的固定指令中。不能靠把它们预写进新版 prompt 来恢复成绩。
- v6 曾要求首轮组合候选；v11 已改为由证据决定。取消这项预设符合
  用户约束，不能因为单次成绩更差就恢复强制组合。
- 完整当前源码、基于原始父版本的累计差异审查、结构化响应错误恢复、
  修复不计研究轮次、相邻轮次连续恶化停止规则，应继续保留。
- v6 最大单次请求为 446,536 字符，v11 为 84,190 字符。限制上下文规模
  有必要；本次纠正的是信息选择，不能全量退回巨大历史转储。

## 已完成与验证

本次代码修改集中在 `src/methodtrail/agents.py` 与
`src/methodtrail/path_graph.py`，增加 5 个针对上述机制的回归测试。
核心测试 **52 个全部通过**，Ruff 检查通过。

本地只读日志审计及变换回放的证据文件：

- `cache/audits/v6_v11_design_audit_before.json`：修复前统计及上下文回放。
- `cache/audits/design_fix_replay.py` 与 `.json`：同一输入的校准和上下文修复回放。

以上 cache 文件与历史运行不提交仓库；测试和本报告记录关键可复现行为。
历史代码、运行、失败路径和预测均保留。

下一次性能验证应固定任务合同、数据划分、模型和预算，分别比较旧压缩
与修复后的结构信息、旧迁移与修复后的迁移；使用独立项目和预先固定的
seed，记录重复运行的波动。恢复信息和纠正错误评分是已完成的工程修复，
恢复 0.314828 的性能尚待独立评测，不能用测试通过替代性能证据。
